# Remaining authorization boundaries (#10)

This guide specifies authorization boundaries and deferred observations, not a completed physical acceptance report. Current serving uses the Docker gateway/offline worker and supports free or prepaid Solana devnet-USDC access; internal TEST_CREDIT fixtures remain useful regressions. Use [current distribution](../distribution.md) and [payments](../payments.md). Earlier native observations and injected-clock/component fixtures do not establish current Docker live startup-binding, natural 24-hour expiry, rate-cap or two-host acceptance.

## Startup binding

Execution requires the grant's provider/startup/model binding to match the current daemon. The signed host rechecks it after its initial request read and nonce persistence, and passes a guard into the daemon's serialized admission decision. A restart/retest during storage I/O cannot admit an old-startup grant into the new startup. Invalid initial bindings consume no nonce or execution authorization; a nonce already durably consumed before a later binding failure remains consumed. Use a new proof nonce when retrying a separately authorized operation.

Retrieval/cancellation is deliberately different: a fresh action grant remains bound to the original stored request, quote, reservation, buyer and original startup. A newer transport can reach that record, but rewriting the action grant to the current startup is rejected. Completed work stays completed; cancellation does not replace its terminal event or rerun inference. Existing cloud authorization independently rechecks the current registered startup before execution.

## Action-grant expiry

The original purchase grant permits actions for at most 24 hours. The provider accepts a fresh operation proof one millisecond before its grant expires, rejects it at the exact expiry, and checks both signed windows again after asynchronous reads and nonce writes. The daemon also rechecks signed authority inside admission/cancellation after its serialized read, immediately before deciding a state change. A proof valid at the host's first read cannot authorize a later expired cancellation or new admission. Once a valid decision has been made, its durable write can finish later; this does not authorize another decision.

The original execution deadline is separate and much shorter. Renewing retrieval/cancellation authority does not renew execution. Existing accounting retrieval issues action-only grants with a two-minute window, preserving original request/startup/reservation bindings and `executeBefore`; the provider rejects their use for `run_inference`. The buyer facade retrieves through refreshed authority and never repurchases or replays a dispatched request automatically.

Result retention is a separate 24-hour window measured from the stored update time. Grant renewal can expose retained metadata/receipt state; it cannot recreate output already purged under retention. Tests preserve the original terminal event when result cleanup removes output. Do not interpret the buyer's mocked retrieval response as proof of live post-retention result availability.

## Accepted-request rate cap

The prototype permits six accepted requests per rolling 60 seconds for an authenticated buyer key at this provider. Fresh peer proofs, request IDs or a new host startup do not create another rate bucket for that key. Another enrolled buyer has an independent bucket; the device's active/queue bounds still apply globally. Accepted failures and cancellations count; rejected requests, duplicate retrieval and duplicate execution of a recorded request do not acquire another slot. Rejected requests still use the existing durable zero-charge failure/outbox path when authenticated.

Admission timestamps now persist in the existing encrypted request record. Launch restores the recent window before testing/publishing the new startup. Explicit declines record `admittedAt: null` and do not become accepted requests after restart. Older records without that field use their last update time conservatively; this can temporarily restrict an upgraded host more than the exact original admission time would. Retests retain the current window. A slot opens when its admission is exactly 60,000 milliseconds old; completions or terminal delivery do not reset its time. No cloud schema or pricing change is required.

## Focused checks and evidence labels

- Signed-host fixtures verify old-startup execution rejection, original-startup retrieval, startup changes during request/nonce I/O, both actions at the exact 24-hour boundary, scoped renewal, and expiry before daemon admission/cancellation decisions.
- The rate fixture verifies six accepted requests, typed seventh-request failure with a failed terminal, idempotent retry/retrieval, another buyer, restart, 59,999-millisecond rejection and 60,000-millisecond admission. Provider fixtures cover conservative legacy records and exclusion of explicit declines.
- Buyer fixtures verify refreshed action-only authority after a simulated 24-hour interval with no additional purchase or inference.
- Added opt-in Postgres regressions verify startup change after purchase leaves execution unauthorized/hold intact, and post-24-hour renewal preserves the original signed grant and receipt. These transaction tests are written but not run in this batch.
- The failure-fixture report now has separate component groups for these boundaries, while their live E2E entries remain `not_run`. Injected clocks are never labeled a natural 24-hour wait.

## Deferred live protocol

Use reviewed merged source, a verified Volcano release, pinned real model/MCPWire, isolated TEST_CREDIT fixtures and the manual two-host setup. Keep original signed grants, keys, connection descriptors and request payloads only in the private evidence directory. Retain redacted IDs, timestamps, source/release identities and observed ledger counts in shared evidence.

1. **Startup binding:** purchase an unexecuted request under startup A, then normally stop only the owned idle provider and restart with its original data/key. Require startup B's new capability/probe/publication. Send a fresh signed operation using A's original grant through B's current transport. Require execution-binding rejection, no worker generation, no authorization/settlement and no fabricated terminal. Observe actual reservation state; do not manufacture a refund to clean up. Separately complete a request under A, reconnect after restart and retrieve it with fresh original-request action authority. Attempting to rewrite its startup must fail; completed cancellation must preserve the existing receipt/event.
2. **Natural 24-hour action expiry:** complete a bounded request and privately retain its original platform-signed purchase grant and exact expiry. Verify both actions with fresh buyer proofs shortly before that expiry. Resume at or after the recorded expiry using the unchanged original signed grant and fresh proofs; require rejection. Do not backdate/re-sign the grant or change either Mac's clock. If the before-expiry window is missed, report it as unobserved. Obtain renewed action-only authority through the ordinary accounting retrieval path, confirm its two-minute limit/original bindings, and verify it cannot execute. Check metadata/receipt separately from output retention. No 24-hour timer, scheduled job or cloud hold is started by this implementation.
3. **Rate cap:** with a freshly verified provider and otherwise eligible buyer, execute six separately purchased bounded requests within one real rolling minute through distinct peer connections. Record admission/terminal timestamps. Submit a seventh valid reserved request while still inside the window; require `RATE_LIMITED`, no extra worker generation and a zero-charge failed outcome. Retrieve/retry that same request without acquiring a slot. Reconnect/restart the idle provider and use new-startup grants inside the original window; the same buyer must remain capped. Verify another enrolled buyer independently, then a new request after the oldest real admission passes 60 seconds. Do not expect the old seventh request to execute on retry; it already has a durable failure. If elapsed startup/testing makes the restart window impossible to observe, record that blocker rather than compressing the clock.
4. After each case, inspect real request/nonce state, receipts, settlement counts, balances and held-reservation/ledger invariants. Confirm no duplicate execution/debit, retain uncertainty for audited reconciliation, stop only owned fixtures and leave shared services healthy.

The existing `fault-seams` command covers its previously documented tamper/proof/execute-before/queue cases; it does not run this natural 24-hour protocol or certify these new live observations. Follow this protocol after batch finalization and attach actual observations to #10 before marking the corresponding gates complete.
